# ESCALATION ESC-002 — v5.3.0 §16–§20 pipeline architecture is doc-surface, not shipped code

Raised 2026-05-21 during Build Mode, Phase 3→4 (translator + pipeline + matcher
+ evidence ledger). County: duval_fl. Framework v5.3.1.

## Context

The operator's Step 2 instructed, in order:

    a. Build the clerk_official_records translator applying the §17 debtor
       party rules and the §18 signal aggregation key.
    b. Run the pipeline: raw clerk events → translator → <source>_leads_base.json
       → aggregator → matched_leads.json. Aggregator reads only base files (§19).
    c. Phase 4 matcher: join clerk events to gis_parcels enrichment.
    d. Evidence ledger for REVIEW_GATE_4.

## Finding — the instructed architecture is not implemented

A codebase search of `scaffold/` confirms the v5.3.0 §16–§20 + §4.34 Build Mode
Protocol architecture exists as CONTRACT DOCUMENTATION only. It is not
implemented in the executable pipeline:

    leads_base        -> 0 hits in scaffold/pipeline/; appears only in
                         scaffold/tests/v5_3_0/test_build_mode_protocol_present.py
    matched_leads     -> 0 hits in scaffold/pipeline/; appears only in v5_3_0
                         doc-presence tests + ops/semantic_verify_template.py
    aggregator        -> 0 hits anywhere in scaffold/pipeline/
    idempotency (§19) -> 0 hits in pipeline code; only the v5_3_0 doc-presence test
    §17 debtor rules  -> 0 hits in scaffold/pipeline/ (no debtor / filer_suppression
                         / filer_entity / owner_type engine)
    §18 aggregation   -> 0 hits in scaffold/pipeline/ (no (parcel_id,
                         canonical_doc_type, signal_type) aggregation engine)

The `scaffold/tests/v5_3_0/` files are named `test_*_present.py` — they assert
the v5.3.0 architecture DOCUMENTS exist, not that the machinery runs. This is
consistent with v5.3.0's own stated scope: §4.39 — "v5.3.0 does NOT ship a
working production semantic verifier — the contract surface only"; §4.21 — "the
operational scripts ship as stubs"; README — "v5.3.0 ships the contract surface
and a documentation-grade reference implementation template."

## What IS shipped and works

The executable pipeline is the v5.1.2-beta **monolithic orchestrator**
(`scaffold/pipeline/build_leads.py`):

    config-driven translator dispatch  (lookup_translator by name)
      -> all_signals  (in-memory, no per-source base file)
      -> _apply_parcel_master_matching   (Phase 4 matcher — SHIPPED, works)
      -> run_pipeline  (score / stack / classify / evidence ledger — SHIPPED)
      -> data/leads.json + data/evidence.jsonl + heartbeat + run manifest

So Step 2c (matcher) and Step 2d (evidence ledger) exist and work. Step 2a
(translator) and Step 2b (the base-file / aggregator / matched_leads pipeline
shape, with §17 + §18 applied) do not — that machinery would have to be built.

Two further gaps surfaced while scoping Step 2a:

  1. No clerk-recordings translator exists. The built-ins are
     `foreclosure_notices`, `parcel_master`, `csv_static_list`. The schema
     translator enum lists `publicsearch_clerk_recordings` but no such module
     exists (and `publicsearch` is itself a vendor-name flagged in the v5.3.0
     Known Issues, item 2).
  2. `build_leads.py` imports only the built-in translator registry. It does
     NOT auto-import county-custom translators from `scrapers/`. A clerk
     translator must therefore either be added as a built-in under
     `scaffold/pipeline/translators/` or `build_leads.py` must be patched to
     import the county module — both are universal-framework changes.

## Why this is a halt, not a workaround

Following Step 2 literally requires building, as NEW universal framework code in
`scaffold/pipeline/`: a §17 debtor-party-rules engine, a §18 signal-aggregation
engine, a per-source `*_leads_base.json` stage, a standalone aggregator with the
§19 idempotency self-check, and the `matched_leads.json` output — i.e. a
multi-contract pipeline subsystem, plus a re-wiring of `build_leads.py`.

MASTER_PROMPT §7 is explicit: "No silent architecture change. Do not create
parallel systems. ... If a proposed change conflicts with existing architecture
documented in FRAMEWORK_VERSION.json or in any KB file, stop and ask the
operator before patching." Building that subsystem mid-county-build, or instead
silently substituting the shipped monolithic pipeline, both violate the
operator's standing "no workaround, no fabrication" rule. This is an
operator-level architecture decision.

## Operator decision required

  - **A — Authorize building the §16–§20 / §4.34 pipeline subsystem** as a
    deliberate universal-framework addition (debtor party rules, signal
    aggregation, aggregator + idempotency, `*_leads_base.json` /
    `matched_leads.json`, translator wiring). This is a framework build in its
    own right and should be scoped, change-manifested, and gated separately —
    not improvised inside the Duval county build.

  - **B — Authorize using the shipped v5.1.2-beta monolithic pipeline** for
    Duval (translator → `run_pipeline` → `leads.json` + `evidence.jsonl`).
    This produces scored, matched leads and an evidence ledger for
    REVIEW_GATE_4, but does NOT produce `*_leads_base.json` / `matched_leads.json`
    and does not apply §17/§18 as discrete contract stages. The clerk
    translator would still need a framework home (built-in or import patch).

  - **C — Defer** the §16–§20 implementation to a framework patch cycle (as the
    `bexar_tx` defect was deferred to v5.3.1), and hold the Duval build at
    Phase 3-complete until that lands.

No framework file has been modified. No translator has been built yet — its
framework home depends on this decision. Build Mode is halted at Step 2.
